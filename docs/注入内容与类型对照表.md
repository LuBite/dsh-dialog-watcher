# 注入内容与类型对照表

> 适用版本：**dsh-dialog-watcher v1.1.1**
> 本文所有「注入全文」都由 `lib/templates.js` 的模板函数**实际渲染产出**（非手工转述）；时间戳为渲染样例时刻，实际注入时为弹窗出现的时间。

---

## 一、按什么维度区分

**主维度 = 归属证据等级（strong / medium / weak / none）。** 弹窗类型（`kind`）是次级维度，只在 **strong** 这一支上起作用：

- **strong** — 按弹窗类型分流（SmartScreen 有专属模板、安装类追加强制规则）
- **medium** — **不区分弹窗类型**，所有类型共用同一份委婉文案
- **weak / none** — **不注入**
- 另有一类与等级无关的通知：**弹窗消失**（只发给"曾注入过"的窗口）

---

## 二、总表

| 等级 | 弹窗类型 | 使用模板 | 与同等级其它类型的差异 | 全文 |
|---|---|---|---|---|
| **strong** | `app-error` | `strongNotice` | 基准形态 | §A |
| **strong** | `installer-wizard` | `strongNotice` | **追加【安装行为处置规则】4 条** | §B |
| **strong** | `smartscreen` | `smartScreenNotice` | 专属模板：开头不同、**必带安装规则**、结尾给"可点仍要运行"的说明 | §C |
| **strong** | `credential` | `strongNotice` | 与基准相同（仅"分类"一行显示"凭据请求"） | §D |
| **strong** | `system-modal` | `strongNotice` | 与基准相同（仅"分类"一行显示"系统对话框"） | §E |
| **strong** | `system-consent` | `systemConsentNotice` | 专属模板：开头不同、**必带「允许/取消」的持久后果说明**、按钮按位置认 | §I |
| **medium** | 除 `system-consent` 外的任意类型 | `mediumNotice` | 开头"**可能**与你有关"，结尾让模型自行判断 | §F / §G |
| **medium** | `system-consent` | `systemConsentNotice`（tentative） | **仍用专属模板**（后果说明不能省），只把归属措辞改成委婉口吻 | §J |
| weak | 任意 | —— | 不注入，进「未归属池」 | — |
| none | 任意 | —— | 不注入，仅 debug 模式写日志 | — |
| 与等级无关 | 曾注入过的窗口消失 | `goneNotice` | 一句话解除通知 | §H |

> **注意**：`INSTALL_RULES`（那 4 条"用户没许可就别继续"的强制规则）只出现在 §B（安装向导）和 §C（SmartScreen）。**§F/§G 的中等证据不带这 4 条**。

### §H gone（弹窗消失通知）

只对**曾被注入过**的窗口发送；没注入过的窗口消失只写事件日志，不打扰会话。

```text
[事件提醒] 此前提醒的弹窗（setup_x64.exe「安装失败」）已被处理，窗口已消失，相关阻塞已解除。无需进一步操作。
```

### §I system-consent（系统安全询问）· 强证据 —— 专属模板

这是 Windows 11「Windows 安全中心」的询问卡片（防火墙放行等）。它与其它类型最大的不同是：**选择会产生持久后果，且系统只问一次**，所以模板必须先把后果讲清再给建议。

```text
[事件提醒] 系统弹出了一个安全询问窗口（Windows 安全中心），正在等待用户选择。
- 分类：系统安全询问（窗口类 Shell_SystemDialogProxy）
- 窗口句柄：0x7A15C6
- 程序：PickerHost.exe（PID 46388）
- 路径：C:\Windows\System32\PickerHost.exe
- 标题：Windows 安全中心
- 正文：Windows 安全中心
- 可点按钮：
- 按钮#1(左)（像素坐标 180,520, L3 高风险 —— 等于授权启动或提权。仅在用户目标明确要求且理由充分时点，并在回复里说明你点了什么）
- 按钮#2(右)（像素坐标 485,520, L1 安全 —— 可以自行点击，无需顾虑）
- 时间：2026/11/1 10:45:02 出现，仍在显示
- 归属依据：强 —— 弹窗进程启动时刻落在你 3 秒前开始的命令执行区间内（firewall 询问由该命令拉起的 node.exe 触发）

【这类窗口的特殊后果 · 与普通报错框不同】
- 选择「允许」→ 为该程序写入**永久放行**规则，外部主机可以连入该程序监听的端口；
- 选择「取消」→ 为该程序写入**永久阻止**规则；
- 同一个程序路径**只会询问一次**，选完不再弹；之后想改只能由用户到防火墙设置里手动调整。
- 按钮文字拿不到（界面由 XAML 绘制，不暴露给 Win32/UIA），按钮只能按位置认：**最左=允许，最右=取消**。

处置建议：
- 若这次监听端口是你任务的正常需要、且用户已认可 → 可点最左按钮（L3 高风险，须在回复里说明你点了什么）；
- 其余情况一律点最右按钮（取消）—— 它只是不允许外部连入，不影响本机向外访问；
- 拿不准就向用户说明并等待指令，**不要擅自放行**。
```

## 四、强 / 中 / 弱 的判定条件

判定在 `lib/attributor.js` 的 `classify()` 中，**按下列顺序短路**，命中即返回。

### 4.1 判定顺序

| 顺序 | 等级 | 判定条件 | 注入文本里的「归属依据」 |
|---|---|---|---|
| **0** | **strong** | 该程序（exe 全路径 / exe 文件名 / SmartScreen 应用字段）被**人工绑定**到某会话 | 程序标识「X」已被人工绑定到该会话 |
| **1** | **strong** | **弹窗进程自身**带 `DSH_SESSION_ID`。该变量由 DSH 注入每条会话命令、并由整棵进程树继承，读到即确定是哪个会话启动的进程 —— **不依赖命令文本** | 弹窗进程本身带会话标记（X.exe），即该会话的命令启动的进程 |
| **2** | **strong** | **拦截器弹窗**：窗口属于防火墙 / UAC / SmartScreen / 杀软，且"被拦截一侧"的进程里**只有一个**会话的 `DSH_SESSION_ID` | 拦截类弹窗（宿主进程 X），被拦截程序一侧的进程带会话标记，唯一指向该会话 |
| 2b | medium | 同上但出现 ≥2 个会话 | 拦截类弹窗：N 个会话都有相关进程，候选不唯一 |
| 3 | **strong** | **SmartScreen「应用」字段**与会话命令里出现过的文件名精确匹配，且时间窗覆盖弹窗（**两个时刻任一对上即可**） | SmartScreen「应用」字段「X」与该会话命令中的文件名精确匹配，且时间窗吻合 |
| 3b | medium | 同上但命中 ≥2 个会话 | 命中 N 个会话的命令线索，候选不唯一 |
| 4 | **strong** | **弹窗进程的 exe** 出现在某会话命令文本里，且那条命令的区间覆盖弹窗（**进程创建时刻或弹窗出现时刻，任一对上即可**） | 窗口进程 X.exe 由该会话的命令「…」带起（命令线索命中且时间窗吻合） |
| 4b | medium | 同上但命中 ≥2 个会话 | exe 命中 N 个会话的命令线索，候选会话不唯一 |
| 5 | **strong** | **owner 链**：弹窗的 owner 进程是某会话命令里出现过的程序 | 弹窗的 owner 进程（X.exe）属于该会话的账本命令 |
| 6 | medium | **仅时间线索**：弹窗落在唯一一个会话的命令区间内（**进程创建时刻或弹窗出现时刻，任一对上即可**） | 弹窗进程创建时刻 / 弹窗出现时刻，落在该会话命令「…」的执行区间内（仅时间线索） |
| 6b | medium | 时间窗命中 ≥2 个会话 | 时间窗命中 N 个会话，候选不唯一 |
| 7 | weak | 仅"该会话在弹窗出现前 90 秒内有过活动" | 仅时间接近（会话 90s 内有活动），无进程/文本证据 |
| 8 | none | 以上全不满足 | 无任何会话线索 |

### 4.2 时间窗与两个时间锚

**时间窗**：命令开始前 **2 秒** ~ 命令结束后 **10 秒**（`timeWindowBeforeMs` / `timeWindowAfterMs`）；弱证据看 **90 秒**（`weakWindowMs`）。

判定"某时刻是否落在命令区间内"时，有**两个候选时刻**，任一对上即算覆盖：

| 锚 | 取值 | 适用场景 |
|---|---|---|
| **进程创建时刻** | 弹窗所属 .exe 被创建的时间 | 短命进程（命令拉起的程序）—— 能证明因果 |
| **弹窗出现时刻** | 探针第一次看见该窗口的时间（比真实出现晚 0~5 秒） | 长命进程（几小时前启动的程序、DSH 宿主自己弹的框）—— 唯一可用的依据 |


### 4.3 什么算「exe 出现在命令文本里」

插件从**执行类工具**（bash / pwsh / shell 等）的命令文本里提取程序名：

- 带扩展名的完整路径或裸名：`D:\tools\setup.exe`、`node.exe`
- **常见解释器的裸名**：`powershell`、`pwsh`、`cmd`、`node`、`npm`、`python`、`git` 等约 50 个，但**只取每段命令的第一个 token** —— `node server.js` 能命中，`echo node is great` 不命中

> **注意**：`run_code` 这类工具的 `code` 参数是**源码**，不会产生任何线索。

### 4.4 拦截器弹窗为什么要单独一条

防火墙询问 / UAC / SmartScreen / 杀软拦截窗，**窗口的宿主进程是拦截器本身**：

| 弹窗 | 窗口宿主 | 被拦截的对象 |
|---|---|---|
| Windows 防火墙询问 | `PickerHost.exe` | 想监听端口的那个程序 |
| UAC 提权 | `consent.exe` | 请求提权的程序 |
| SmartScreen | `smartscreen.exe`（有"应用"字段可读） | 被拦的应用 |
| 第三方杀软 | 杀软自己的进程 | 触发拦截的操作方 |

所以"弹窗进程的 exe 出现在命令文本里"这条对它们**原理上永远命中不了**。插件改为：识别出这类弹窗后，**跳过宿主 exe**，转去扫描"哪些进程带 `DSH_SESSION_ID`"，用会话集合是否唯一来判定。

> 注意：第 1 条（读弹窗进程自身）对拦截器弹窗**不适用** —— 窗口的宿主是拦截器进程，它本身不带会话标记，读到的必然是空，于是自然落到第 2 条。

### 4.5 等级 → 动作

| 等级 | 动作 |
|---|---|
| strong | 直接注入 |
| medium | **单次不注入**，挂起等配对；同一程序在同一会话再弹一次、凑齐「双命令双弹窗」并通过 5 条互斥后，才委婉注入；否则超时（默认 10 分钟）入池 |
| weak | 入池（面板里可见，可人工指认建立绑定） |
| none | 丢弃（debug 模式才写日志） |

**去重规则**：只按「**同一个窗口**」去重（同一 hwnd 不重复通知）。**不存在"某个程序注入过一次就永不再通知"这种规则** —— 凡是判定为该会话触发的弹窗，每次都会通知。


## 五、可检测的弹窗类型

### 5.1 基础筛选（先决条件）

一个窗口要被当成"阻塞性弹窗"，必须同时满足：

| 门槛 | 规则 |
|---|---|
| 可见 | `IsWindowVisible` 为真 |
| 非工具窗 | 不带 `WS_EX_TOOLWINDOW` |
| 未被虚拟桌面隐藏 | DWM `DWMWA_CLOAKED` 为 0 |
| 窗口类 | 属于 `#32770`（标准对话框）、`Credential*`、`*TaskDialog*`、`ApplicationFrameWindow`、`Windows.UI.Core.CoreWindow*`、`Shell_SystemDialog*` 之一 |
| 尺寸 | 宽 ≥ 100、高 ≥ 50（**`Shell_SystemDialog*` 豁免**：它的顶层窗口是 `0x0` 空壳，真实尺寸靠命中测试反推） |
| 类名黑名单 | 排除 Shell_TrayWnd / Progman / WorkerW / NotifyIconOverflowWindow / MsftIMEShellWnd / SysListView32 / Shell_SecondaryTrayWnd |
| UWP 宿主黑名单 | 排除 systemsettings / textinputhost / shellexperiencehost / searchhost / startmenuexperiencehost / applicationframehost / runtimebroker / searchapp / windowsinternal.*textinput.inputapp |
| 必须有按钮 | 传统对话框必须能在子控件或 UIA 里找到至少一个按钮（**`Shell_SystemDialog*` 豁免**：既无子控件也无 UIA 按钮，按钮靠像素识别，见 5.3） |
| UWP 窗口 | 只有被判定为 SmartScreen 才上报，其它 UWP 一律不报 |

### 5.2 六种可检测类型

| kind | 分类名 | 判定特征 | 你看到的画面 |
|---|---|---|---|
| `app-error` | 程序错误框 | **兜底类型**：通过基础筛选、有按钮、且不属于下面任何一类 | 最常见的小方框：感叹号/红叉图标 + 一句报错 + 「确定」/「取消」/「重试」。例如"无法启动此程序""连接失败""脚本错误" |
| `installer-wizard` | 安装向导 | **标题 / 正文任一段 / 进程文件名**里出现 `install`、`setup`、`installer` 或中文「安装」 | 安装程序窗口：有"下一步/安装/完成"，标题像"Setup - XXX""某软件 安装"；也可能是装到一半弹出的"安装失败" |
| `smartscreen` | SmartScreen 拦截 | UIA 中出现自动化 ID 为 `moreBtn` / `runBtn` / `dontRunBtn` 的按钮，或元素名含 "Windows Defender SmartScreen" / "Windows 保护了你的电脑" | 蓝色整屏提示「**Windows 已保护你的电脑**」，小字列出应用名与发布者，底部「更多信息」与「不运行」，点开更多信息才出现「仍要运行」 |
| `credential` | 凭据请求 | 窗口**类名以 `Credential` 开头** | 要求输账号密码的框：用户名/密码输入框 + 「确定」「取消」。常见于网络身份验证、映射网络驱动器、企业软件登录 |
| `system-modal` | 系统对话框 | 窗口**类名含 `TaskDialog`** | 系统风格的任务对话框：系统字体标题栏、警告/盾牌图标、正文较长、可能带"不再显示此消息"勾选框 |
| `system-consent` | 系统安全询问 | 窗口**类名以 `Shell_SystemDialog` 开头**，宿主进程是 `PickerHost.exe` | 「Windows 安全中心」卡片：**屏幕中央**的浅色圆角卡片、全屏变暗遮罩、一排两个按钮。例：「是否要允许公共网络和专用网络访问此应用?」（防火墙询问）、「此应用想要访问你的位置」 |

> **判定的先后顺序**：SmartScreen → **系统安全询问** → Credential → TaskDialog → 安装关键词 → 兜底为程序错误框。因此一个"安装向导"如果同时被识别为 SmartScreen，会走 SmartScreen 分支。

> **关于 `system-consent` 的归属**：它的宿主进程固定是 `PickerHost.exe`（拦截器），
> 所以「弹窗进程的 exe 出现在命令文本里」这条对它永远不成立；它的归属走 **§4.4 拦截器弹窗** 的规则，
> 不看宿主 exe，而是看"被拦截一侧哪些进程带会话标记"。

### 5.3 系统安全询问卡片是怎么被识别并点击的

这类卡片的窗口结构很反常，识别与点击都做了专门处理：

| 事实 | 实测数据（3840×2160 @150%） |
|---|---|
| 可枚举到的顶层窗口 | `Shell_SystemDialogProxy`，尺寸 **0x0**，**没有任何子窗口** |
| 真正显示内容的卡片 | `Shell_SystemDialog`，实测 669×582 居中——**`EnumWindows` 与 `EnumThreadWindows` 都枚举不到**（666 个顶层窗口里没有它） |
| 全屏遮罩 | `Shell_SystemDim`，0,0,3840,2160——同样枚举不到 |
| UIA | 只返回 1 个 `Pane`，边界报 `Infinity`；桌面树里查不到该进程的元素；**按钮文字完全拿不到** |
| 遮罩是否挡住点击 | **不挡**。`WindowFromPoint` 在卡片区域返回卡片本身，卡片是独立窗口盖在遮罩之上（早期"遮罩拦截"的结论是坐标错位导致的误判） |

因此插件分四步处理：

1. **检测**：以 `Shell_SystemDialogProxy` 为锚点
2. **定位**：`WindowFromPoint` 网格采样（步长随屏幕尺寸缩放）求包围盒，再对四条边二分精化到 **±1px**
3. **找按钮**：GDI 截取卡片 → 取**卡片左右边距的颜色**作基线（那几列永远是按钮行底面的颜色）→ 比基线亮 5 以上算按钮 → 在**底部带（高度 80%~96%）**内做**列投影**找按钮矩形
   - 不能用全卡统计：卡片正文与按钮行是**两种不同的底色**，且**哪种更亮取决于主题** —— 浅色下正文 255 > 按钮 250，深色下正文 43 ≈ 按钮 45，任何全局阈值都会失效
   - 不能用 Otsu：它把按钮的**文字**当成暗类（实测 T=86），分的是「字 vs 面」而不是「面 vs 按钮」
   - 不能用单行扫描：行若穿过按钮文字，会把一个按钮切成两段（实测 2 个按钮变 4 段）
   - 只能搜底部带：卡片最底一行的描边、以及上方正文区，都会污染带检测
4. **点击**：在按钮中心 `SetCursorPos` + `mouse_event` 发真实点击，点击前用 `WindowFromPoint` 复核该点仍属于本卡片

全程坐标运行时测量、无硬编码像素值，且探测器启动即 `SetProcessDPIAware()`，换分辨率/缩放不需要改代码。

## 六、按钮安全等级

注入里每个按钮都带一个等级。绝大多数类型按按钮**文字**匹配得出；系统安全询问卡片拿不到文字，**按位置**判定（见下表下方说明）：

| 等级 | 触发文字 | 注入里显示的建议 |
|---|---|---|
| **L3** | 含「仍要运行 / run anyway / 允许 / allow / trust / 信任」，或含「安装 / install / 下一步 / next / elevat」 | L3 高风险 —— 等于授权启动或提权。仅在用户目标明确要求且理由充分时点，并在回复里说明你点了什么 |
| **L1** | 含「取消 / cancel / 不运行 / don't run / 否 / no / 关闭 / close / 忽略 / ignore」 | L1 安全 —— 可以自行点击，无需顾虑 |
| **L2** | 其它（含「确定 / ok / 继续 / continue / 是 / yes / 重试 / retry」以及所有未匹配的） | L2 中等 —— 判断是否推进任务所必需；不必要时优先取消 |

**按位置判定（仅 `system-consent`）**：按钮文字拿不到，按钮名形如 `按钮#1(左)` / `按钮#2(右)`。Windows 各语言版本都是**最左=肯定（允许/确定）、最右=否定（取消/拒绝）**，因此：

| 按钮名 | 等级 | 说明 |
|---|---|---|
| `按钮#N(右)`（最后一个） | **L1** | 否定动作。对防火墙询问就是「取消」= 写入永久阻止规则 |
| `按钮#N(左)`（其余） | **L3** | 肯定动作。对防火墙询问就是「允许」= 写入永久放行规则 |
| `按钮#1`（只有一个按钮时） | L2 | 无法判断语义 |

等级**只改变建议措辞**，是否点击始终由模型判断（插件不做规则化代点）。
